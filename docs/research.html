🔬 Research

The problem & the data

Why this is a ranking problem, not a single yes/no question

An agency managing editorial calendars doesn't do it for one site — it does it across many client portfolios at once. This page lays out the real problem behind Content Refresh, and the dataset used to study it.

The content problem

A large content library decays unevenly. Some pages keep earning search visibility indefinitely; others quietly lose ground for months before anyone notices. An editorial team can't manually re-check every page on a fixed schedule, so the practical question isn't "is this page declining?" in isolation — it's "out of everything, what should we look at first?"

The dataset behind this project reflects that scale: 30,000 anonymized pages spanning 32 distinct client portfolios, not one large site. A fixed policy like "refresh anything older than a year" wastes review time on pages that are still performing, while a page quietly losing visibility on a different client's site can sit unreviewed for a full cycle. That scheduling problem, at portfolio scale, is the case study this project works through.

Problem framing

Unit of analysis

One row is one content page.

Output

A ranked queue — each page gets a decline-probability score, a reason code, and a recommended action.

Action a human takes

An editor works down the queue and reviews flagged pages against the stated reason — the model narrows the list, a person decides.

Cost of a wrong call

A false positive costs review time; a false negative delays review of a page that needed it. Neither is severe alone.

Dataset

content_refresh_anonymized.csv, the safe starter release for the Content Refresh lane: 30,000 rows, 44 columns. All content_id and client_id values are pre-anonymized hashes; no raw client names, URLs, or search queries appear anywhere in this dataset or the repository.

Deliberately excluded from the model's features:

  • content_id, client_id — identifiers, not predictive signal
  • trend_direction, trend_pct — describe the outcome trend directly and would leak the label
  • The six 30-day window columns used to build the target
Leakage caught and corrected. An earlier draft defined the target identically to the baseline rule and included those same columns as model inputs. That version scored a perfect 1.0000 across every metric — not a good result, but a deterministic function of its own inputs. It was discarded in favor of the independent, forward-looking target used throughout this project. See Methodology for the full target definition.
